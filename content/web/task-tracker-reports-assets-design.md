[6탄](/wiki/web/task-tracker-notes-heatmap)까지는 "기록을 쌓는" 기능이었다. 이번엔 쌓인 기록을 **보고할 수 있는 형태**로 바꾸는 게 목표였다. 사내 IT 담당자가 인정받는 순간은 대개 보고서와 증적에서 나온다. 그런데 보고서를 만들려고 보니, 그 전에 데이터 모양부터 고쳐야 했다.

## 1. 장비·솔루션 항목: 보고서 이전의 문제

보안·인프라 업무에는 "장비 및 솔루션 명"을 적는 칸이 있었다. 그냥 글자 칸이라 같은 방화벽이 어떤 날은 `FW-01`, 어떤 날은 `fw 01`로 들어갔다. 이 상태로 "장비별 장애 건수"를 세면 같은 장비가 두 줄로 갈라진다.

그래서 환경설정에 **장비·솔루션 항목**을 등록하는 곳을 만들고, 업무는 이름 대신 항목 id(`assetId`)를 들고 있게 했다. id로 세면 나중에 항목 이름을 바꿔도 집계가 흔들리지 않는다.

### 기존 업무는 이름으로 이어 붙인다

이미 쌓인 업무에는 id가 없다. 전부 다시 고르게 할 수는 없으니, 이름을 정규화해서 같은 분류의 같은 이름 항목에 연결했다.

```ts
/** 대소문자·공백·하이픈·밑줄·점 차이는 같은 이름으로 본다. (FW-01 = fw 01 = FW_01) */
export function normalizeAssetName(name: string): string {
  return name.toLowerCase().replace(/[\s\-_.]/g, "");
}
```

같은 정규화로 항목 등록 때 중복도 막는다. 그리고 업무에는 적혀 있는데 아직 등록 안 된 이름은 "업무에만 적혀 있는 이름"으로 건수와 함께 모아 보여주고, 누르면 한 번에 등록되게 했다. 처음 쓰는 날 기존 데이터를 옮기는 작업이 몇 번의 클릭으로 끝난다.

### 이름을 바꾸면 연결이 끊기는 문제

테스트 중에 구멍을 하나 찾았다. `NAS-01`을 등록해서 기존 업무 2건이 연결된 걸 확인하고, 이름을 `NAS-01 본관`으로 바꿨더니 연결 업무가 **0건**이 됐다. 기존 업무는 id 없이 이름으로만 붙어 있었으니 당연한 결과였다.

그래서 항목 이름(또는 분류)을 바꾸기 **직전에**, 지금 이름으로 연결된 업무들에 id를 먼저 기록하도록 했다. 내용 수정이 아니니 업무의 수정 시각과 이력은 건드리지 않는다.

```ts
if (nextName !== asset.name || nextCategory !== asset.category) {
  await assertUnique(nextName, nextCategory, id);
  const allAssets = await store.list();
  const nameLinked = (await listTasks()).filter(
    (t) => t.assetId !== id && resolveAssetId(t, allAssets) === id
  );
  await assignAssetId(nameLinked.map((t) => t.id), id);
}
```

이 흐름은 PGlite 테스트에 "이름을 바꿔도 연결 유지, 수정 시각은 그대로, 다른 분류 업무는 건드리지 않음"으로 고정해 뒀다.

## 2. 월간 보고서

항목이 생기자 월간 보고서는 **입력 없이** 만들 수 있었다. 리포트 탭 아래에 하위 탭을 두고, 달을 넘기면 이런 순서로 계산된다.

1. 요약: 완료, 신규 접수, 장애 대응, 월말 진행 중, 평균 처리 기간, 당일 처리율
2. 분류별 완료와 전월 대비 증감
3. 장비·솔루션별 전체 / 장애 / 작업 건수
4. 장애 내역
5. 주요 완료 업무
6. 다음 달 마감 예정
7. 특이사항(직접 입력)

타이머 없이 처리 기간을 구할 수 있었던 건 **접수일(신청일, 없으면 등록일)과 완료일의 날짜 차이**로 계산했기 때문이다. 이 앱은 헬프데스크처럼 일이 수시로 끼어드는 흐름이라, 시간을 재는 방식은 처음부터 맞지 않았다.

### "월말 진행 중"은 지금 진행 중과 다르다

지난달 보고서를 열었을 때 "진행 중"을 **지금** 상태로 세면 틀린다. 9월 29일에 접수해 10월 1일에 끝낸 업무는, 9월 말 기준으로는 진행 중이었다. 테스트를 쓰면서 이 케이스에서 기대값을 처음에 틀리게 적었는데, 계산이 맞고 테스트가 틀린 쪽이었다.

```ts
const openAtEnd = tasks.filter((t) => {
  if (receivedKey(t) > end) return false;
  const done = completedKey(t);
  return !done || done > end;
});
```

날짜 키는 5탄 잔디 때처럼 전부 로컬(KST) 날짜로 만든다. 한국 시간 10월 1일 새벽 0시 30분에 끝낸 업무가 UTC 기준으로 9월 완료에 섞이지 않게 테스트로 막아 뒀다.

## 3. 장애 보고서

장애로 등록한 업무마다 보고서를 붙였다. 필드는 발생·복구 일시, 영향 범위, 원인, 조치 내용, 재발 방지 대책이다. 업무와 항상 같이 읽고 쓰니 별도 테이블 대신 업무에 jsonb로 넣었다.

- 발생·복구 시각은 `datetime-local` 입력값(`YYYY-MM-DDTHH:mm`)을 그대로 저장한다. 시간대 변환이 끼어들 틈을 아예 없앴다.
- 처음 열면 업무 기록으로 채운다. 발생은 등록 시각, 복구는 완료 시각, 조치 내용은 작업 내용과 완료 메모.
- 복구가 발생보다 빠르면 장애 시간을 계산하지 않고 경고한다.
- 문서번호는 `INC-202609-01`처럼 그달 발생 순서로 매긴다.

### 인쇄가 곧 PDF

두 보고서 모두 "PDF로 저장"은 결국 `window.print()`다. 대신 인쇄용 CSS를 따로 줬다.

- 메뉴·버튼·토스트는 `print:hidden`으로 뺀다.
- 다크 모드로 보고 있어도 종이에는 **라이트 팔레트**로 찍히게, `@media print`에서 색 토큰을 덮어쓴다.
- 인쇄 직전에 `document.title`을 바꿨다가 `afterprint`에서 되돌린다. PDF 파일 이름이 `장애보고서_INC-202609-01`처럼 나온다.

## 4. 디자인 정리

기능을 빠르게 붙이다 보니 화면이 조금씩 제각각이 됐다. 이번엔 새 기능 없이 다섯 가지를 한 번에 손봤다.

### 작은 글씨와 흐린 글씨

10~11px 글씨가 90군데 넘게 있었고, 흐린 글씨 색 `#9c8a76`은 아이보리 바탕에서 명암비가 **3.2:1**이었다. 작은 글씨 권장 기준은 4.5:1이다. 최소 크기를 12px로 올리고 색을 `#7a6a58`로 바꿔 4.9:1이 됐다. 같은 갈색 계열이라 인상은 거의 그대로다.

### 공통 부품과 색의 역할

버튼·카드·입력칸·세그먼트·칩을 `@layer components`에 공통 클래스로 만들고, 스크립트로 반복되던 클래스 문자열을 바꿨다(버튼 23곳, 카드 23곳, 입력칸 22곳). Tailwind v4에서 컴포넌트 레이어는 유틸리티보다 앞이라, 각 자리의 `flex-1`이나 `w-full` 같은 레이아웃 클래스는 그대로 덮어쓴다.

정리하면서 색의 역할도 정했다. **주 버튼은 헤더의 "새 업무"와 같은 먹색, 초록은 완료·선택됨 같은 상태에만.** 예전엔 업무 상태 버튼에서 "진행중"을 골라도 초록으로 칠해져서 완료처럼 보였다.

### 대시보드는 "지금 처리할 것"부터

화면 가운데를 크게 차지하던 날짜 인사말을 한 줄로 줄이고, 맨 위에 **지금 처리할 것**을 뒀다. 마감 지남 → 오늘 → 우선순위 상 세 묶음이고, 한 업무는 가장 급한 묶음 하나에만 들어간다.

### 뼈대 로딩과 빈 화면

"불러오는 중…" 글자는 실제 모양을 흉내 낸 회색 뼈대로 바꿨다. 스크린리더에는 `role="status"`로 "불러오는 중"만 알린다. 빈 화면에는 다음 행동 버튼을 달았다("반복 업무 추가", "첫 메모 쓰기").

### 휴대폰: 시트와 떠 있는 버튼

휴대폰에서는 모든 창이 아래에서 올라오는 시트가 된다. Radix Dialog는 그대로 두고, 640px 미만에서만 위치·모서리·등장 애니메이션을 바꿨다. 새 업무는 오른쪽 아래에 떠 있는 + 버튼으로 옮기고, 토스트와 하단 여백은 버튼과 겹치지 않게 올렸다.

### 하루씩 밀려 있던 마감 표시

대시보드를 확인하다가 오늘 마감인 업무가 "D-1"로 나오는 걸 봤다. 원인은 마감일 23:59:59와 지금 시각의 차이를 **올림**한 계산이었다.

```ts
// 예전: 오늘 마감 → 0.4일 → 올림 1 → "D-1", 어제 마감 → -0.6일 → 올림 0 → "오늘 마감"
const days = Math.ceil((due.getTime() - now.getTime()) / 86400000);
```

오늘은 D-1, 어제 마감은 "오늘 마감", 이틀 지난 건 "1일 지남"으로 전부 한 칸씩 밀려 있었다. 두 곳에 복사돼 있던 이 함수를 하나로 합치고, 시각이 아니라 **로컬 날짜끼리의 차이**로 계산하게 바꿨다. 자정 직후·직전 경계도 테스트에 넣었다.

## 마무리

이번 작업의 순서가 곧 교훈이었다. 보고서를 바로 만들었다면 장비 이름이 갈라진 표가 나왔을 것이다. **데이터 모양 → 계산 → 화면** 순서로 가니 월간 보고서는 입력 없이 나왔고, 디자인 정리는 남은 버그까지 드러내 줬다. 모든 계산은 순수 함수로 빼서 `npm test`에 6개 묶음으로 들어가 있다.
