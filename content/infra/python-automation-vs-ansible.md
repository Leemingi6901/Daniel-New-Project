## 배경

폐쇄망(에어갭) 환경의 RHEL/Rocky Linux 서버 여러 대를 관리하면서, Docker·Python·커널·NVIDIA GPU 드라이버를 최신 버전으로 맞추는 작업을 자동화해야 했다. 인터넷이 안 되는 네트워크라 어떤 도구를 쓰든 결국 "인터넷 되는 PC에서 필요한 파일을 미리 받아서, 폐쇄망으로 옮기고, SSH로 설치"하는 2단계 구조는 피할 수 없었다.

이 작업을 Python + paramiko(SSH 라이브러리)로 직접 짜고 나서, "이거 앤서블(Ansible)로 했으면 더 나았을까?"라는 질문을 스스로에게 던지게 됐다. 결론부터 말하면 **부분적으로는 맞고, 부분적으로는 틀렸다.** 이 글은 그 경계선을 실제 작업 경험을 바탕으로 정리한 것이다.

## 무엇을 만들었나

핵심은 IP 목록을 입력하면 각 서버에 병렬로 SSH 접속해서 다음을 자동으로 처리하는 스크립트였다.

- **Docker**: 현재 버전 확인 → 최신 버전이면 스킵 → 아니면 `live-restore`를 활성화해 무중단으로 바이너리 교체 → 업데이트 전후 실행 중이던 컨테이너를 스냅샷 비교해서 빠진 게 있으면 자동 재기동
- **Python**: `/opt`에 새 버전을 설치하고 심볼릭 링크를 갱신, 버전 비교로 이미 최신이면 스킵
- **Kernel**: RPM은 설치하되 재부팅은 별도 스크립트로 분리 (재부팅 후 SSH 재연결을 폴링하며 새 커널 적용을 검증)
- **GPU Driver + CUDA**: nouveau 블랙리스트, `kernel-devel → glibc → glibc-devel → libmpc → gcc` 순서로 의존성 설치(EL9의 CC 새니티체크 실패를 우회하기 위한 순서), 버전 서브폴더 자동 탐지, 실패 시 로그 자동 덤프

여기에 `daemon.json`의 커스텀 설정(`data-root` 등)을 실수로 날리지 않기 위한 안전한 파싱/백업 로직, 통합 리포트 출력까지 포함하면 스크립트 하나가 1,200줄이 넘어갔다. 개별 자동화 스크립트 각각의 상세 개발기는 [Docker](/wiki/infra/docker-auto-install-airgap), [Python](/wiki/infra/python-auto-install-airgap), [GPU](/wiki/infra/gpu-auto-install-airgap) 문서에 따로 정리해뒀고, 이 글은 그 전체를 다 만들고 난 뒤 앤서블과 비교한 회고다.

## 앤서블이었다면 공짜로 얻었을 것들

이 작업을 다 만들고 나서 보니, 표준적인 패키지 관리 시나리오에서는 앤서블이 이미 검증된 기능을 제공한다는 게 보였다.

**멱등성이 기본 제공된다.** `yum`/`dnf` 모듈에 원하는 버전을 지정하면, 이미 그 버전 이상이면 알아서 아무것도 안 한다. 지금 스크립트에서는 이걸 위해 버전 문자열을 튜플로 바꿔 비교하는 헬퍼 함수를 직접 만들어야 했다.

**재부팅 대기/검증이 내장돼 있다.** `ansible.builtin.reboot` 모듈은 재부팅 실행 → 연결 끊김 감지 → 재연결 폴링 → 타임아웃까지 한 번에 처리한다. 커널 업데이트 스크립트에서 SSH 재연결을 직접 폴링하며 새 커널 버전을 검증하는 로직을 손으로 짰는데, 이게 앤서블에선 모듈 하나다.

**인벤토리/병렬 처리가 명령줄에서 바로 된다.** `hosts` 파일에 OS 버전별, GPU 유무별로 그룹을 나눠두면 `--forks`로 병렬 수를, `--limit`으로 대상 서버를 커맨드라인에서 바로 조절할 수 있다. 지금은 이걸 IP 리스트 파일과 `ThreadPoolExecutor`로 직접 구현했다.

**dry-run이 된다.** `--check` 모드로 실제 적용 없이 뭐가 바뀔지 미리 확인할 수 있다. 지금 스크립트엔 이런 기능 자체가 없다.

## 앤서블로 가도 결국 손으로 짜야 하는 부분

반대로, 이 프로젝트에서 실제로 가장 어려웠던 부분은 앤서블을 썼어도 크게 달라지지 않았을 거라고 본다.

NVIDIA `.run` 설치 파일의 CC 새니티체크 실패를 우회하기 위한 의존성 설치 순서, nouveau 블랙리스트 등록, 커널 모듈 언로드 시 발생하는 경합 처리 같은 건 앤서블에서도 결국 `shell`/`command` 태스크를 그대로 나열하는 수밖에 없다. Ansible Galaxy에 NVIDIA 관련 role이 있긴 하지만, 오프라인 `.run` 파일 + 버전 서브폴더 자동 탐지 같은 폐쇄망 특유의 요구사항엔 맞지 않아서 어차피 직접 짜야 했을 것이다.

버전 서브폴더에서 `.run` 파일을 정규식으로 찾아 자동 선택하는 것 같은 동적 분기 로직도, YAML + Jinja2로 표현하면 오히려 더 읽기 어려워진다. 이런 조건 분기는 Python의 `if`/`for`가 훨씬 자연스럽다.

컨테이너 자동 복구(업데이트 전후 스냅샷 비교 후 재기동), Docker/Python/Kernel/GPU를 한 테이블에 모은 통합 리포트도 앤서블의 기본 출력으로는 안 나온다. 커스텀 콜백 플러그인을 만들거나, 결국 후처리 스크립트를 따로 짜야 하니 지금처럼 Python으로 결과를 모아 보여주는 것과 큰 차이가 없다.

## 앤서블이 아예 안 맞는 영역

이번 프로젝트엔 서버 디스커버리 스크립트도 있었다. IP 대역을 스캔해서 접속 가능한 서버를 찾아내고, 하드웨어/소프트웨어 정보를 모아 엑셀 리포트로 만드는 작업이다. 앤서블은 인벤토리가 이미 있다는 전제로 동작하는 도구라서, 이렇게 "인벤토리를 처음부터 찾아내는" 작업 자체는 지원 범위 밖이다.

실행 중 대화형 입력이 필요한 로직도 마찬가지다. GPU 버전 서브폴더가 여러 개 발견됐을 때 사람이 골라야 하는 상황을, 병렬/무인 실행에서는 앤서블도 Python도 똑같이 처리할 수 없다. 결국 자동 선택 + 경고 로그로 타협하는 수밖에 없었다.

## 결론: 우열이 아니라 역할 분담

정리하면, 이번 작업의 약 80%를 차지하는 "표준적인 패키지 설치 + 버전 관리 + 재부팅" 같은 부분은 앤서블이 이미 만들어둔 바퀴를 손으로 다시 만든 셈이었다. 이 부분만 놓고 보면 앤서블 쪽이 더 성숙한 도구인 게 맞다.

하지만 이 프로젝트의 진짜 난이도였던 나머지 20%, 그러니까 GPU 드라이버 설치 체인이나 폐쇄망 특유의 예외 처리는 어느 도구를 썼어도 비슷한 수준의 커스텀 로직이 필요했을 것이다. 그래서 "Python으로 직접 짠 게 실력이 부족해서"가 아니라, "이 프로젝트가 요구하는 복잡도의 상당 부분이 애초에 범용 도구로 흡수되지 않는 영역이었다"는 게 더 정확한 결론이다.

다음에 비슷한 규모의 폐쇄망 자동화를 다시 한다면, Docker/Python/Kernel처럼 표준화가 잘 되는 부분은 앤서블로 옮기고, GPU 드라이버처럼 복잡한 셸 로직이 핵심인 부분만 Python 스크립트로 남기는 하이브리드 구성을 고려해볼 만하다.
