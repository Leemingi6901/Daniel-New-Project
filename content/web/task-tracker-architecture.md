[1탄](/wiki/web/task-tracker-vercel-blob-consistency)부터 [8탄](/wiki/web/task-tracker-audit-neon-backup)까지는 그때그때 만든 기능을 적었다. 입사(10/12)를 앞두고 구성이 거의 굳었으니, 이번 편은 기능 소개가 아니라 **설계 문서**다. 무엇이 어디서 돌고, 각 부분이 어떤 규칙으로 판단하는지를 적는다. 나중에 내가 잊었을 때 이 글 하나로 다시 이해할 수 있어야 한다.

## 0. 목표와 원칙

목표는 두 가지다.

1. **업무 누락 방지:** 받은 요청이 기록되지 않거나, 기록된 일이 마감을 넘기지 않게 한다.
2. **고과 증적:** 반기·연간에 "무엇을 얼마나 했는지"를 숫자와 목록으로 바로 꺼낼 수 있게 한다.

설계 원칙은 네 가지로 정했다.

- **혼자 쓰는 앱이다.** 사용자 관리, 권한 체계, 멀티테넌시는 만들지 않는다. 그 대신 "나만 쓸 수 있다"는 보장은 단단하게 한다.
- **비용 0원.** 모든 구성 요소를 무료 플랜 한도 안에 둔다. 한도는 설계 조건으로 다룬다.
- **특정 업체에 갇히지 않는다.** Vercel이 멈춰도 GitHub의 코드와 백업만으로 다른 PC나 호스팅에서 다시 띄울 수 있어야 한다.
- **판단 로직은 순수 함수로.** 날짜 계산, 알림 계획, 보고서 집계, 글 해석은 저장소를 건드리지 않는 함수로 빼고 테스트로 고정한다.

## 1. 전체 구성

```
                 ┌──────────── 사용자 ────────────┐
                 │ 웹/PWA      슬랙 DM     텔레그램 │
                 └────┬──────────┬───────────┬────┘
                      │          │ 서명       │ 비밀 헤더
                      ▼          ▼           ▼
   cron-job.org ──▶ ┌──────────── Vercel (Next.js 16) ─────────────┐
   (15분 tick)      │ proxy.ts: 세션 쿠키 검사 / 외부 경로는 통과     │
                    │ /api/cron/tick   /api/slack/*  /api/telegram/* │
   Vercel Cron ───▶ │ /api/cron/due-alerts(09시대) archive-done(08시) │
                    │ /api/cron/backup ◀──────── GitHub Actions      │
                    └──────────┬────────────────────────┬───────────┘
                               │ Drizzle (neon-http)    │ 알림
                               ▼                        ▼
                         Neon Postgres           슬랙 / 텔레그램 API
                                                       
   GitHub 저장소: main(코드) ── 푸시 = Vercel 배포
                 backups(데이터) ── snapshots/날짜.json (하루 두 번)
```

| 구성 요소 | 역할 | 요금제 |
|---|---|---|
| Vercel | Next.js 앱, API, 하루 한 번 도는 크론 2개 | Hobby(무료) |
| Neon | Postgres. 운영 데이터 | Free |
| GitHub | 코드(main), 백업(backups 브랜치), Actions | 비공개 저장소 무료 |
| cron-job.org | 15분마다 알림 tick 호출 | 무료 |
| Slack(개인 워크스페이스) | 알림 받기, 명령어 | Free |
| Telegram | 명령어(알림은 끔) | 무료 |

앱 화면은 대시보드, 업무 관리(업무·반복 업무·메모·매뉴얼·라이선스·입퇴사), 보고서(일일·주간·월간·장애·성과 요약), 기록(잔디), 환경설정으로 나뉜다. 이 글은 화면보다 그 뒤의 동작을 다룬다.

## 2. 저장소: 인터페이스 하나, 백엔드 셋

모든 데이터(업무, 일정, 반복 업무, 메모, 장비, 라이선스, 매뉴얼, 입퇴사, 알림 기록, 백업 기록)는 같은 인터페이스를 거친다.

```ts
interface Collection<T extends { id: string }> {
  get(id: string): Promise<T | null>;
  list(): Promise<T[]>;
  put(record: T): Promise<void>;        // 덮어쓰기(upsert)
  create(record: T): Promise<boolean>;  // 같은 id가 없을 때만 만든다
  remove(id: string): Promise<void>;
}
```

`DATA_STORE` 환경 변수로 백엔드를 고른다.

| 값 | 백엔드 | 쓰는 곳 |
|---|---|---|
| `postgres` | Neon + Drizzle | **현재 운영** |
| (없음) | Vercel Blob(레코드 하나 = JSON 파일 하나) | 10/1 전까지 운영 |
| `file` | `local-data/컬렉션.json` | 복구용 로컬 실행 |

- **스위치는 일부러 명시적이다.** `DATABASE_URL`이 생기는 순간 자동으로 Postgres로 바꾸지 않는다. Neon을 연결하자마자 빈 DB로 서비스되는 걸 막기 위해서다.
- **`create()`가 따로 있는 이유:** 알림 중복 방지 같은 "선점"이 필요해서다. 백엔드마다 원자적으로 구현한다.
  - Postgres: `INSERT … ON CONFLICT DO NOTHING RETURNING id`의 결과 행 수
  - Blob: `allowOverwrite: false`로 쓰고, 실패하면 `head()`로 이미 있는지 확인
  - 파일: 파일별 쓰기 큐 안에서 확인 후 추가
- **표 변경은 배포가 한다.** `npm run build`가 `scripts/db-migrate.ts`를 먼저 돌려 drizzle 마이그레이션을 적용한다. 실패하면 빌드가 멈추니, 표와 안 맞는 코드가 배포되지 않는다.

## 3. 인증: 들어오는 길마다 다른 열쇠

| 들어오는 곳 | 인증 방법 |
|---|---|
| 웹 화면·앱 API | 비밀번호 로그인 → httpOnly 세션 쿠키. `proxy.ts`가 모든 요청에서 검사 |
| `/api/cron/backup`, Vercel 크론 | `Authorization: Bearer CRON_SECRET` |
| `/api/cron/tick` | `TICK_SECRET` 또는 `CRON_SECRET` |
| 캘린더 구독 피드 | URL 토큰 = HMAC(SESSION_SECRET, "calendar-feed") |
| 텔레그램 웹훅 | 헤더 `X-Telegram-Bot-Api-Secret-Token` = HMAC(봇 토큰, "telegram-webhook") + 내 채팅 ID |
| 슬랙 | `v0=HMAC_SHA256(signing secret, "v0:{timestamp}:{본문}")`, 5분 넘은 요청 거절 + 내 멤버 ID |

규칙 몇 가지를 지킨다.

- **최소 권한:** 외부 스케줄러(cron-job.org)에는 `TICK_SECRET`만 넣는다. 이 키가 새도 "보낼 알림 있는지 확인"만 할 수 있고, 백업 API는 못 부른다.
- **새 환경 변수를 늘리지 않는 파생 키:** 캘린더 토큰과 텔레그램 웹훅 비밀값은 이미 있는 비밀값에서 HMAC으로 만든다.
- **비교는 상수 시간:** 모든 비밀값 비교는 `timingSafeEqual`로 한다. Bearer 비교는 양쪽을 sha256으로 같은 길이로 만든 뒤 비교한다.
- **붙여 넣기 실수에 관대하게:** 대시보드에 키를 붙여 넣으면 끝에 줄바꿈이 섞이거나, 환경 변수에 `Bearer `까지 같이 들어가는 일이 생긴다. 비교 전에 둘 다 걷어 낸다.
- **실패 진단:** 인증에 실패하면 키 값이 아니라 **모양만** 기록한다(`Bearer 형식인지, 받은 길이, 기대 길이`). 실제로 cron-job.org에서 401이 계속 났을 때, 이 기록에 "둘 다 64자"가 찍혀서 키를 저장하지 않은 게 원인이라는 걸 바로 알았다.
- **로그인 보강:** 틀린 비밀번호는 0.8초 늦게 답하고, `X-Frame-Options: DENY`로 iframe에 넣지 못하게 한다.

## 4. 알림 엔진

알림은 4종류다.

| 종류 | 보내는 때 | 내용 |
|---|---|---|
| 업무 일보 | 평일 09~12시 첫 tick | 어제(월요일은 금~일) 완료, 반복 업무 수행률과 놓친 것, 마감 지남, 오늘 마감, 우선순위 상, 오늘 일정, 입퇴사 체크리스트, 라이선스 만료 임박, 내일 마감, 진행 중 건수 |
| 주간 요약 | 금요일 일보와 함께 | 이번 주 완료, 다음 주 마감 |
| 반복 업무 알림 | 매일 17~22시 첫 tick | 아직 체크 안 한 반복 업무 + 완료 버튼 |
| 회의 알림 | 07~22시, 시작 60분 전부터 시작 전까지 첫 tick | "N분 후 회의", 장소, 참석자 |

### tick 한 번의 흐름

cron-job.org가 15분마다 `/api/cron/tick`을 부르면 이 순서로 판단한다.

```
1. 시간대 확인(notifyWindows)     → 일보·반복·회의 셋 다 시간 밖이면 끝(DB 안 읽음)
2. 오늘 보낸 기록 확인(한 건 조회) → 일보·반복 업무를 이미 보냈으면 그 데이터는 안 읽음
3. 필요한 컬렉션만 읽기           → 일보면 업무·일정·반복·라이선스·입퇴사, 회의면 일정만
4. 계획(planNotifications)        → 순수 함수. 보낼 메시지 목록과 key
5. key마다 기록 선점(create)       → 실패하면 다른 tick이 보내는 중이라 건너뜀
6. 발송(notifyAll)                → 실패하면 선점을 풀어 다음 tick에 재시도
```

- **key가 곧 중복 방지다.** `daily:2026-10-13`, `weekly:2026-10-16`, `recurring:2026-10-13`, `meeting:{id}:{날짜}T{시각}` 같은 key 하나당 기록이 하나다. 회의 key에 시각이 들어 있어서, 회의 시간을 바꾸면 key가 달라져 다시 알린다.
- **선점 후 발송:** 09시에 Vercel 크론과 tick이 동시에 들어와도 `create()`는 한쪽만 성공한다. "확인 → 보내기 → 기록" 순서였던 처음 구현은 둘 다 확인을 통과할 수 있었다.
- **시간대가 있는 이유:** 서버가 멈췄다가 밤에 깨어나도 그날 일보를 밤에 보내지 않는다. 오전에 내내 멈췄다면 그날 일보는 건너뛴다.
- **시간대 밖에서는 DB를 아예 안 깨운다.** Neon은 5분 동안 요청이 없으면 잠든다. 22시~07시 tick은 1단계에서 끝나니 밤새 DB가 잔다.
- **한국 시간:** 서버는 UTC로 돈다. 날짜와 시각은 전부 `kstNow()`로 KST로 바꿔서 판단한다. 처음엔 `toLocaleDateString()`을 그대로 써서 09시 전엔 "오늘"이 어제가 되는 버그가 있었다.
- **예비 경로:** Vercel 크론(하루 한 번, 09시대)도 같은 tick 처리를 부른다. cron-job.org가 멈춰도 일보는 나간다. 이미 보냈으면 기록이 있어서 두 번 가지 않는다.

### 여러 메신저로 보내기

`NOTIFY_TO=slack`처럼 받을 곳을 고르고, 없으면 연결된 메신저 모두로 보낸다. 실패 처리 규칙이 핵심이다.

- **전부 실패:** 오류를 던진다. 선점을 풀고 다음 tick에 재시도한다.
- **일부만 실패:** 보낸 것으로 친다. 다시 보내면 이미 받은 쪽에 같은 알림이 또 가기 때문이다. 실패는 기록만 남긴다.

### 왜 cron-job.org인가

처음엔 GitHub Actions의 `schedule`로 tick을 돌렸다. 그런데 같은 저장소의 백업 기록을 보니 이랬다.

- 00시 예약 실행이 **4시간 44분 늦게** 돌았다.
- 12시 예약 실행은 **아예 안 돌았다.**

GitHub 문서에도 부하가 높으면 예약 실행이 늦어지거나 빠질 수 있다고 되어 있다. 회의 60분 전 알림에는 쓸 수 없는 정확도라 cron-job.org로 옮겼다. 백업은 몇 시간 늦어도 괜찮아서 GitHub에 두되, 붐비는 정각을 피해 매시 17분으로 옮겼다.

## 5. 메신저 봇

슬랙과 텔레그램에서 같은 명령어를 쓴다. 명령어 로직은 `botCore`에 한 벌만 있고, 메신저별 코드는 받는 방식과 보여 주는 방식만 다르다.

| 명령어 | 하는 일 |
|---|---|
| `/add 내용` | 업무 등록. 글에서 마감, 분류, 우선순위를 읽는다 |
| `/memo 내용` | 메모 게시판에 저장. 첫 줄이 제목 |
| `/today` | 업무 일보와 같은 내용 + 남은 반복 업무 체크 버튼 |
| `/list` | 진행 중 업무(마감 가까운 순, 최대 15개) + 완료 버튼 |
| `/done 이름` | 오늘 반복 업무 체크 또는 업무 완료 |
| `/help` | 명령어 안내(예시 포함) |
| 명령어 없는 글 | [업무로 등록] [메모로 저장] 버튼으로 묻기 |

### 글 해석기: "MD팀 VPN 계정 요청 내일까지 #지원 !"

순수 함수 `parseTaskText(글, 오늘)`이 이 순서로 걷어 낸다.

1. **분류 태그:** `#보안` `#인프라` `#지원`(IT 지원) `#기타`. 모르는 태그는 제목에 남긴다.
2. **우선순위:** 따로 떨어진 `!`, 또는 "긴급·급함·급건"이 있으면 상.
3. **마감:** 아래 규칙을 순서대로 시도하고, 처음 맞는 하나만 쓴다. 뒤에 "까지"가 붙어도 되고, 앞뒤가 공백이나 글 끝이어야 한다. 그래서 "오늘의 이슈"는 마감으로 보지 않는다.

| 쓴 말 | 해석 |
|---|---|
| `2026-11-30` | 그 날짜(없는 날짜면 무시) |
| `10/15`, `10.15`, `10월 15일` | 올해 그 날. 이미 지났으면 **내년** |
| `오늘`·`금일`, `내일`, `모레` | 오늘 + 0·1·2일 |
| `금요일` | 오늘부터 처음 오는 금요일. 오늘이 금요일이면 오늘 |
| `이번주 금요일` | 이번 주(월요일 시작)의 금요일 |
| `다음주 월요일` | 다음 주의 월요일 |

남은 글자가 제목이다. 위 예시는 제목 "MD팀 VPN 계정 요청", 마감 내일, 분류 IT 지원, 우선순위 상이 된다.

### `/done`의 찾기 규칙

1. 후보는 **오늘 해당하는데 아직 안 한 반복 업무**와 **진행 중 업무**다.
2. 이름 비교는 공백과 대소문자를 무시하고 일부만 맞아도 된다("백업점검" → "서버실 백업 점검").
3. 딱 하나 맞으면 바로 처리하고, 여러 개면 버튼으로 고르게 한다. 하나도 없으면 `/list`, `/today`를 안내한다.

### 버튼

버튼 데이터는 `r:{반복업무id}:{날짜}`(체크)나 `t:{업무id}`(완료)다. 텔레그램 제한인 64바이트 안에 들어간다. 반복 업무 버튼에 날짜를 넣은 이유는, 17시 알림을 다음 날 아침에 눌러도 **알림이 온 날**에 체크되게 하기 위해서다. 누르면 그 버튼만 메시지에서 빠지고 결과 한 줄이 붙는다.

### 메신저별 차이

| | 텔레그램 | 슬랙 |
|---|---|---|
| 받는 곳 | 웹훅 1개 | 슬래시 명령·버튼·이벤트 3개 |
| 응답 제한 | 느리면 같은 update를 다시 보냄 | **3초 안에** 응답해야 함 |
| 처리 | 처리 후 200 | 바로 빈 200을 주고 `after()`로 처리, 결과는 `response_url`로 |
| 중복 방지 | `update_id` 선점 | `event_id` 선점 |
| "업무로 등록" 버튼의 원래 글 | 질문을 원래 메시지의 **답장**으로 보내고 `reply_to_message`에서 꺼냄 | 버튼 value(최대 2,000자)에 원래 글을 실음 |
| 메시지 모양 | HTML(`<b>`, `<code>`) | 같은 HTML을 mrkdwn으로 바꿔 Block Kit 섹션(3,000자씩) |

중복 방지는 알림과 같은 `claimOnce(key)`(= `create()`)를 쓴다. 저장소 기능 하나가 알림 중복, 메신저 재전송 중복을 모두 막는다.

## 6. 반복 업무 계산

반복 업무는 일정 규칙과 완료한 날짜 목록(`doneDates`)만 들고 있다. "오늘 해당하는가"는 순수 함수가 계산한다.

| 주기 | 해당하는 날 |
|---|---|
| 매일 | 시작일 이후 전부 |
| N일마다 | (오늘 − 시작일) % N = 0 |
| 매주 | 고른 요일 |
| 매월 | 고른 날짜(없으면 시작일의 날짜) |

- 체크는 날짜 하나를 켜고 끄는 방식이라, 화면에서 목록 전체를 보내 다른 날 기록을 덮어쓰는 일이 없다.
- 성과 요약에서 반기·연간 수행률을 내야 해서, 완료 기록은 800일 동안 남긴다.

## 7. 보고서와 성과 요약

보고서도 전부 저장소를 안 건드리는 집계 함수다. 성과 요약(반기·연간)은 이렇게 센다.

| 지표 | 계산 |
|---|---|
| 완료 건수 | 기간 안에 완료한 업무 |
| 마감 준수율 | 마감일이 있는 완료 업무 중 마감일 안에 끝낸 비율 |
| 평균 처리일·당일 처리율 | 시작일부터 완료일까지의 날 수 |
| 반복 업무 수행률 | 해야 했던 횟수 대비 한 횟수. 진행 중인 기간이면 **오늘까지만** 센다 |
| 장애 | 건수, 평균 복구 시간, 장애 보고서 작성률 |
| IT 지원 | 부서별·유형별 건수 |
| 입퇴사 | 처리 인원, 체크리스트 기한 준수율, 기한 지나서도 안 한 항목(누락) |
| 주요 업무 | 장애 > 우선순위 상 > 결과 메모가 있는 것 순 |

결과는 그대로 마크다운으로 내보낼 수 있어서 고과 자기 평가에 바로 붙여 넣는다.

## 8. 백업과 복구

```
GitHub Actions (00:17·12:17 KST 무렵)
  └─ GET /api/cron/backup  (Bearer CRON_SECRET)
       └─ 모든 컬렉션 → JSON 하나 {app, version, exportedAt, store, counts, collections}
  └─ backups 브랜치 snapshots/YYYY-MM-DD.json 커밋 (같은 날 이전 버전은 커밋 이력)
  └─ POST /api/cron/backup → 환경설정 "마지막 자동 백업" 기록
```

안전장치는 세 겹이다.

1. **빈 백업 거부:** 백업 기록 자체도 레코드라서 정상이면 0건일 수 없다. 지난 백업이 있었는데 0건이 오면 API가 503을 준다. 워크플로가 재시도하고, 빈 파일은 커밋되지 않는다.
2. **급감 경고:** 전날보다 30% 넘게 줄면 워크플로가 경고를 남긴다.
3. **복구 쪽 방어:** `npm run restore`는 0건 스냅샷을 건너뛰고, 급감한 스냅샷이면 전날 것을 쓰라고 안내한다.

복구는 새 PC 기준으로 이렇다. 10/1에 빈 폴더에서 실제로 해 봤고, `.env.local` 없이 데이터 15건이 그대로 떴다.

```bash
git clone …/daniel-work-tracker && cd daniel-work-tracker && npm ci
npm run restore     # backups 브랜치 최신 → local-data/
npm run dev:local   # 로컬 파일 저장소로 실행, 로그인 비밀번호는 자동 생성
```

## 10. 테스트

`npm test`에 15묶음이 있다. 대부분 순수 함수 테스트이고, 몇 개는 로컬 파일 저장소와 가짜 외부 API로 전체 흐름을 돌린다.

- **알림 백테스트:** 2주를 5분마다 돌리면서 동시 tick, 서버 멈춤, 발송 실패, 토큰 누락, 늦은 회의 등록을 섞고, 모든 알림이 정확히 한 번 나가는지 본다.
- **메신저:** 글 해석, 웹훅·슬랙 서명, 명령어별 처리, 버튼, 재전송 중복, 일부 메신저 실패를 검증한다.
- **백업:** 모든 컬렉션이 백업 목록에 들어 있는지 확인한다. `blobCollection(...)` 선언을 코드에서 찾아 비교하기 때문에, 새 컬렉션을 만들고 백업에 안 넣으면 테스트가 깨진다.

## 마무리

정리하고 보니 이 앱의 뼈대는 세 가지다.

1. **저장소 인터페이스 하나:** 백엔드를 바꿔도(Blob → Neon → 로컬 파일) 위쪽 코드는 그대로다.
2. **key 하나 = 기록 하나:** 알림 중복, 메신저 재전송, 동시 tick을 전부 같은 `create()` 선점으로 막는다.
3. **판단은 순수 함수, 실행은 얇게:** 날짜, 알림 계획, 글 해석, 집계를 테스트로 고정해 두니, 슬랙을 붙일 때도 받는 부분만 새로 쓰면 됐다.
