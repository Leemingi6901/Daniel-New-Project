[7탄](/wiki/web/task-tracker-reports-assets-design)까지는 기능을 붙이는 이야기였다. 10월 12일부터는 이 앱에 진짜 업무를 적는다. 그 전에 던진 질문은 하나였다. **"여기에 실제 업무를 맡겨도 되나?"** 기록이 빠지거나 날아가면 누락 방지도, 고과 증적도 의미가 없다.

그래서 이번엔 기능 대신 세 가지를 했다. 장애가 나면 되살리는 길을 먼저 만들고, 시스템을 점검하면서 알림을 2주치 돌려 보고, 마지막으로 저장소를 바꿨다.

## 1. Vercel이 끊겨도 되살릴 수 있게

먼저 정한 기준은 "Vercel 구독이 끊겨도 GitHub에서 코드를 받아 로컬에서 바로 돌릴 수 있을 것"이었다.

### 백업은 GitHub의 별도 브랜치에

GitHub Actions가 하루 두 번(00시·12시 KST) 앱의 백업 API를 부르고, 받은 JSON을 같은 저장소의 `backups` 브랜치에 `snapshots/날짜.json`으로 커밋한다. 코드가 있는 `main`과 데이터가 섞이지 않고, 같은 날 이전 버전은 커밋 이력에 남는다.

```yaml
on:
  schedule:
    - cron: "0 15 * * *" # 00:00 KST
    - cron: "0 3 * * *"  # 12:00 KST
```

백업 커밋마다 Vercel이 배포를 시도하지 않도록 `backups` 브랜치에는 `{"git": {"deploymentEnabled": false}}`짜리 `vercel.json`을 같이 넣는다. 전날보다 레코드가 30% 넘게 줄면 워크플로가 경고를 남긴다.

### 복구는 명령 두 줄

저장소에 세 번째 백엔드로 **로컬 파일 저장소**(`DATA_STORE=file`)를 만들었다. 컬렉션 하나가 JSON 파일 하나다. 그러면 복구는 이렇게 끝난다.

```bash
npm run restore     # backups 브랜치의 최신 스냅샷 → local-data/
npm run dev:local   # 로컬 파일 저장소로 앱 실행
```

같은 백업 파일을 `--target postgres`로 넣으면 운영 DB 복구도 된다. 절차는 저장소의 `RECOVERY.md`에 적어 뒀고, 환경설정 화면에는 "마지막 자동 백업" 시각이 보인다.

## 2. 점검: 가장 큰 구멍은 코드가 아니라 요금제였다

점검하면서 무료 한도를 실제 사용량으로 계산해 봤다. Vercel Blob Hobby의 한도는 이렇다.

| 종류 | 무엇이 해당되나 | 월 한도 |
|---|---|---|
| Advanced | `put`, `list` | 2,000회 |
| Simple | `head`, 캐시 미스 읽기 | 10,000회 |

넘으면 **30일 동안 Blob이 막힌다.** 문제는 목록 읽기 구조였다. [1탄](/wiki/web/task-tracker-vercel-blob-consistency)에서 `list()`의 메타데이터가 늦게 갱신되는 걸 피하려고, 목록에서는 id만 얻고 내용은 레코드마다 `head()` + `fetch`로 다시 읽게 해 뒀다. 정확하지만 비싸다.

- 업무 300건이면 대시보드를 한 번 열 때 simple op가 **약 600회** 든다.
- 한 달 한도 10,000회는 화면을 **20번도 못 열고** 끝난다.
- 백업은 컬렉션 12개를 안정될 때까지 여러 번 훑느라 한 번에 `list`가 50회를 넘었다. 하루 두 번이면 **백업만으로 월 2,000회**를 쓴다.

코드로 아낄 수는 있어도 근본 해결은 아니었다. 결론은 **입사 전에 Neon(Postgres)으로 옮기기**. 그 전까지 쓸 Blob 쪽 절약도 같이 넣었다.

- **백업은 `data/` 한 번에 훑기:** 컬렉션마다 따로 `list`하지 않고 전체 경로를 한 번에 받아 경로 앞부분으로 나눈다. 백업 한 번에 `list` 50회 이상이 몇 회로 줄었다.
- **캘린더 구독 피드는 CDN 캐시:** 애플 캘린더는 몇 분마다 피드를 다시 받아 간다. `Vercel-CDN-Cache-Control: max-age=900`으로 15분 동안 같은 응답을 돌려준다. 주소에 비밀 토큰이 들어 있어서 주소별로만 캐시된다.
- **빈 목록이면 다시 묻기:** Blob `list()`는 가끔 통째로 빈 배열을 준다. 이 인스턴스에서 데이터를 본 적 있는 경로만 잠깐 쉬고 다시 묻는다. 정말 빈 컬렉션까지 매번 재시도하면 그것도 한도를 쓴다.

### 알림이 두 번 갈 수 있었다

09시에는 Vercel 크론과 외부 tick이 동시에 들어올 수 있다. 기존 코드는 "보냈는지 확인 → 보내기 → 기록" 순서라, 둘 다 확인을 통과하면 일보가 두 번 간다.

순서를 **선점 → 보내기**로 바꿨다. 저장소 인터페이스에 "같은 id가 없을 때만 만든다"는 `create()`를 추가하고, 백엔드마다 원자적으로 구현했다.

```ts
// Postgres: 이미 있으면 아무것도 안 하고, 넣었는지만 돌려준다
const inserted = await db.insert(table).values(row)
  .onConflictDoNothing({ target: table.id })
  .returning({ id: table.id });
return inserted.length > 0;
```

Blob은 `allowOverwrite: false`로 쓰고, 거절되면 `head()`로 정말 있는지 확인한다. 로컬 파일은 파일별 쓰기 큐 안에서 확인하고 추가한다. 보내는 쪽은 이렇게 된다.

```ts
claimed = await log.create({ id, key: message.key, sentAt: new Date().toISOString() });
if (!claimed) continue;                 // 다른 tick이 보내는 중
const ok = await sendTelegram(message.text);
if (!ok) { await log.remove(id); ... }  // 실패하면 선점을 풀어 다음 tick에 재시도
```

### 그 밖에 잡은 것

- **금요일 주간 요약이 재시도되지 않음:** 주간 요약 계획이 "일보를 아직 안 보냈으면" 블록 안에 들어 있었다. 일보는 나가고 주간 요약만 실패하면 다음 tick에서 다시 만들어지지 않았다. 둘을 따로 보게 고쳤다.
- **보내는 시간대가 없음:** 서버가 멈췄다가 밤에 깨어나면 그날 일보를 밤에 보낼 수 있었다. 이제 일보는 09~12시, 반복 업무는 17~22시, 회의는 07~22시에만 보낸다. 이미 보냈는지는 한 건 조회로 먼저 확인하고, 보냈으면 데이터를 아예 읽지 않는다.
- **빈 백업이 최신 백업을 덮을 수 있음:** 백업 기록도 레코드라서 정상이라면 전체가 0건일 수 없다. 지난 백업이 있었는데 0건이 오면 API가 503을 돌려준다. 워크플로의 `curl --retry`가 다시 시도하고, 빈 파일은 커밋되지 않는다. 복구 스크립트도 0건 스냅샷은 건너뛴다.
- **서버에서 하루 밀리는 날짜:** Vercel 서버는 UTC로 돈다. 라이선스·입퇴사 정렬에 쓰던 `new Date().toLocaleDateString("en-CA")`가 KST 09시 전에는 어제 날짜였다. KST 날짜 함수로 바꿨다.
- **로그인:** 비밀번호를 해시끼리 `timingSafeEqual`로 비교하고, 틀리면 0.8초 늦게 답한다. 잘못된 JSON이 500을 내던 것도 401로 막았다. `X-Frame-Options: DENY`로 다른 사이트가 iframe에 넣지 못하게 했다.

매뉴얼 마크다운 렌더러(React 요소로만 만들고 `http(s)` 링크만 허용)와 캘린더 토큰(HMAC 파생 + 상수 시간 비교)은 점검해 보니 원래 안전했다.

## 3. 알림 2주치 백테스트

단위 테스트는 "이 시각에 무엇을 보낼 계획인가"만 본다. 실제로는 tick이 계속 들어오고, 그 사이에 사람이 체크하고, 서버가 멈추고, 텔레그램이 실패한다. 그래서 `test-notify-backtest`를 만들었다. 로컬 파일 저장소와 가짜 텔레그램(`fetch` 대체)으로 **2주(10/12~10/25)를 5분마다** 돌린다. 일부러 섞은 상황은 이렇다.

| 상황 | 기대 |
|---|---|
| 매 근무일 09:00 tick 두 번 동시 | 일보 한 번 |
| 10/14 서버가 11시에 깨어남 | 11:00에 일보 |
| 10/15 오후까지 멈춤 | 그날 일보 건너뜀 |
| 10/16 09:00 첫 발송 502 | 주간 요약은 09:00, 일보는 09:05 |
| 10/19 09:00~09:10 토큰 없음 | 09:15에 일보 |
| 짝수 날 15시에 반복 업무 체크 | 홀수 날만 17:00 알림(주말 포함) |
| 10/21 13:45에 14:00 회의 등록 | 바로 "15분 후" 알림 |

마지막에 "모든 알림은 딱 한 번", "텔레그램에 실제로 간 글 수 = 보낸 기록 수", "보낸 시각은 모두 07~22시"를 확인한다. 21건이 전부 기대대로 나갔다.

솔직히 처음 돌렸을 때 실패한 두 번은 코드가 아니라 **내 기대값**이 틀린 경우였다. 회의를 등록한 바로 그 시각의 tick이 이미 알림을 보내는데 다음 tick을 기대했고, 22:00 회의가 21:55 알림 목록에 들어오는 걸 빼먹었다. 시뮬레이션은 내가 머릿속으로 그린 동작까지 검증해 준다. 이 테스트도 `npm test`에 들어가서 이제 13묶음이 돈다.

## 4. Neon 전환: 비밀값을 PC에 두지 않고

Neon은 Vercel 대시보드의 Storage → Create Database → Neon(Free)으로 만들었다. 연결하면 `DATABASE_URL`이 환경 변수로 자동으로 들어간다. 코드는 4탄에서 `DATA_STORE=postgres` 스위치로 준비해 둔 상태였다. `DATABASE_URL`만으로 전환하지 않게 한 이유는 연결하는 순간 빈 DB로 서비스되는 걸 막으려는 것이었다.

### 계획대로 안 된 부분

원래 계획은 `vercel env pull`로 DB 주소를 받아 이 PC에서 이관 스크립트를 돌리는 것이었다. 그런데 받아 보니 값이 전부 `"[sensitive]"`였다. Neon 연동 변수는 민감 정보로 잠겨서 내려받을 수 없다. 게다가 이 PC는 회사 컴퓨터라 DB 열쇠를 남기는 것 자체가 좋지 않았다.

그래서 이관을 **Vercel 빌드 안에서** 하게 바꿨다. 빌드에서는 민감 변수도 쓸 수 있다.

```json
"build": "tsx scripts/db-migrate.ts && next build"
```

`db-migrate.ts`가 하는 일은 이렇다.

1. `DATA_STORE=postgres`일 때만 drizzle 마이그레이션을 적용한다. 미리보기 배포나 Blob 운영 중에는 아무것도 하지 않는다.
2. `MIGRATE_FROM_BLOB=1`이면 Blob 전체를 Neon에 복사하고, 다시 읽어 필드 단위로 원본과 대조한다.
3. 하나라도 다르면 빌드를 멈춘다. 배포가 안 되니 앱은 이전 배포(Blob)로 계속 돈다.

먼저 진짜 Blob 데이터를 인메모리 PGlite에 넣는 리허설로 확인했다. 그다음 Vercel에 `DATA_STORE=postgres`와 `MIGRATE_FROM_BLOB=1`을 넣고 푸시했다. 빌드 로그는 이렇게 나왔다.

```
[db-migrate] Neon 표 최신 상태
[db-migrate] ✓ 업무: Blob 9건 → Neon 9건
[db-migrate] ✓ 일정: Blob 2건 → Neon 2건
...
[db-migrate] ✓ 입·퇴사자: Blob 2건 → Neon 2건
```

배포 직후 `MIGRATE_FROM_BLOB`은 지웠다. 복사는 같은 id를 덮어쓰기만 해서 여러 번 돌아도 안전하다. 하지만 남겨 두면 11일에 테스트 데이터를 지운 뒤 다음 배포 때 Blob에서 **되살아난다.** 1회용 스위치는 쓰고 바로 끄는 게 맞다.

이제 표 변경도 따로 할 일이 없다. 새 마이그레이션 파일을 커밋하면 배포 빌드가 적용한다. 실패하면 빌드가 멈추니, 표와 안 맞는 코드가 배포될 일도 없다.

## 5. GitHub 자동 백업 살리기

백업 워크플로는 만들어 놨는데 계속 401이었다. GitHub 저장소 시크릿의 `CRON_SECRET`이 Vercel 값과 달랐던 것이다. Vercel 쪽 값을 보려 했더니 민감 정보라 눈 아이콘이 없었다.

그래서 새 값을 만들어 양쪽에 같이 넣었다. 화면에 띄우지 않고 클립보드로 바로 보내면 어디에도 값이 남지 않는다.

```powershell
([guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')) | Set-Clipboard
```

Vercel(Edit)과 GitHub(Update secret)에 붙여 넣고 재배포한 뒤, 워크플로를 수동으로 한 번 돌렸다. 모든 단계가 통과했고 `backups` 브랜치에 `backup 2026-10-01 13:39 KST (15건)`이 커밋됐다. 스냅샷 안의 `"store": "postgres"`가 운영이 Neon에서 읽고 있다는 증거였다.

## 마무리

이번 작업에서 남은 교훈은 두 가지다.

1. **무료 한도는 설계 조건이다.** 정확성을 위해 넣은 `head()` 한 번이 레코드 수만큼 곱해지니 한 달 한도가 화면 20번이 됐다. 기능을 만들 때 "한 번 열 때 몇 번 읽나"를 같이 세야 한다.
2. **장애 상황은 시뮬레이션으로 돌려 봐야 보인다.** 동시 tick, 실패 후 재시도, 서버 멈춤을 섞어 2주를 돌리니 주간 요약 재시도 누락 같은 구멍이 드러났다.

아직 남은 의존이 하나 있다. 백업도 Vercel의 API를 거치기 때문에 Vercel이 멈추면 새 백업도 멈춘다. 이미 쌓인 백업으로 복구는 되지만, 다음 고도화로 GitHub Actions가 Neon에서 직접 백업받게 바꿀 생각이다. 텔레그램 봇을 만들면 알림 tick도 켠다.
