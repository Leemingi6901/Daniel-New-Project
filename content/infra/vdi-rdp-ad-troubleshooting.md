신규 Active Directory를 구축하고 VDI에 사용자 계정을 만들어 RDP로 접속했는데, ID/PW 인증은 통과하면서도 로그인 화면 직후 "원격 데스크톱 서비스를 통해 로그인할 수 있는 권한이 있어야 합니다" 오류가 떴다. 인증 문제가 아니라 권한 문제라는 확신은 있었지만, 원인을 좁혀가는 과정에서 몇 번을 헤맸다.

## 문제 상황

Windows에서 RDP로 로그인하려면 대상 컴퓨터의 로컬 보안 정책(또는 GPO)에서 다음 두 가지를 만족해야 한다.

- **"원격 데스크톱 서비스를 통한 로그온 허용"** 목록에 계정(또는 소속 그룹)이 포함되어 있을 것
- **"원격 데스크톱 서비스를 통한 로그온 거부"** 목록에는 포함되어 있지 않을 것

기본적으로 이 권한은 `Administrators`와 `Remote Desktop Users` 로컬 그룹에게 부여되어 있다. 신규 계정은 당연히 이 그룹에 속해 있지 않았기 때문에 생긴 문제로 추정하고 확인을 시작했다.

## 확인 과정에서 겪은 삽질들

### 1) 로컬 정책은 도메인 컨트롤러에서 확인할 수 없다

`lusrmgr.msc`를 열었더니 "이 컴퓨터는 도메인 컨트롤러입니다. 이 스냅인은 도메인 컨트롤러에서 사용할 수 없습니다"라는 오류가 떴다. DC에는 로컬 계정/로컬 그룹 개념 자체가 없다. VDI 서버가 아니라 실수로 DC에서 로컬 정책을 열려고 했던 것이 원인이었다. VDI 서버의 권한은 그 서버가 속한 OU에 연결된 **GPO**로 관리해야 한다.

### 2) GPO 우선순위와 OU 상속 구조 확인

그룹 정책 관리(GPMC)에서 확인해보니 `VDI` OU에는 우선순위가 다른 GPO 두 개(상위 OU에서 상속된 것 하나, VDI OU에 직접 연결된 것 하나)가 걸려 있었다. 둘 다 **컴퓨터 구성 → 정책 → Windows 설정 → 보안 설정 → 로컬 정책 → 사용자 권한 할당 → "원격 데스크톱 서비스를 통한 로그온 허용"**이 **"정의되지 않음"** 상태였다. 즉 GPO가 이 권한을 명시적으로 제한하는 게 아니라, 로컬 기본값(Administrators + Remote Desktop Users)이 그대로 유효한 상황이었다.

### 3) 컴퓨터 계정이 VDI OU에 없었다

여기서 진짜 원인을 발견했다. VDI가 AD 자체에서 생성된 게 아니라 **외부 VDI 플랫폼에서 만들어진 뒤 도메인 조인만 되는 구조**였다. 도메인 조인 시 OU를 별도 지정하지 않으면 컴퓨터 계정이 기본 **Computers 컨테이너**에 생성되고, GPO가 걸려있는 `VDI` OU에는 들어가지 않는다.

해결책은 두 가지로 정리했다.

**당장 해당 서버만**: ADUC의 Computers 컨테이너에서 대상 컴퓨터를 찾아 `VDI` OU로 이동 → `gpupdate /force`.

**앞으로 조인되는 VDI들에 자동 적용(근본 해결)**:
```powershell
redircmp "OU=VDI,OU=연구소,OU=Contoso,DC=contoso,DC=local"
```
기본 컴퓨터 조인 위치를 Computers 컨테이너 대신 VDI OU로 리다이렉트한다.

### 4) RDP 인증서 이름이 접속 주소와 다르게 뜨는 현상

포트포워딩된 주소로 접속했는데 인증서 이름이 실제 접속 대상과 다른 호스트명으로 표시되어 당황했다. 오류가 아니라 정상 동작이다 — RDP 자체 서명 인증서의 이름은 접속에 쓴 IP/포트가 아니라 **실제 대상 컴퓨터의 호스트명**을 쓴다. 오히려 이 이름이 AD에서 확인했던 목록과 다르다는 걸 알아채면서 컴퓨터 계정 위치를 재점검하는 계기가 됐다.

### 5) 방화벽이 RDP 포트 하나만 열려 있었다

가장 답답했던 부분. `compmgmt.msc` 원격 연결, PsExec, WinRM 등으로 문제를 해결하려 했지만, 방화벽 정책상 RDP로 매핑된 포트 외에는 전부 차단되어 있어 SMB/RPC/WinRM 기반 원격 관리 도구를 전혀 쓸 수 없었다.

## 최종 해결

1. 문제 계정 대신 **도메인 관리자 계정**으로 동일한 RDP 주소에 접속 — Domain Admins는 기본적으로 로컬 Administrators에 포함되므로 별도 권한 없이 로그인 가능
2. 관리자 세션에서 `lusrmgr.msc` 실행 → **Remote Desktop Users** 그룹에 문제 계정 추가
3. `net localgroup "Remote Desktop Users"`로 반영 확인
4. 로그아웃 후 해당 계정으로 재접속 → 정상 로그인 확인

## 체크리스트

새 AD + 외부에서 프로비저닝되는 VDI 조합에서 RDP 로그인이 안 될 때:

- 오류가 로그인 화면 **이전**인지 **이후**인지로 인증 문제 vs 권한 문제를 먼저 구분한다
- 로컬 정책 확인은 반드시 **대상 서버**에서 (DC에서는 불가)
- 대상 서버가 속한 OU의 GPO에서 "원격 데스크톱 서비스를 통한 로그온 허용/거부" 정의 여부를 우선순위 높은 GPO부터 확인
- 컴퓨터 계정이 실제로 GPO가 걸린 OU에 있는지 확인 — 외부에서 조인만 하는 VDI는 기본 Computers 컨테이너에 남아있을 가능성이 높다
- 필요하면 `redircmp`로 기본 조인 위치를 원하는 OU로 리다이렉트
- RDP 인증서 이름 불일치는 정상 동작 — 실제 접속 대상 호스트명을 확인하는 단서로 활용
- 방화벽이 RDP 포트만 열려있는 폐쇄 환경이라면, 이미 권한 있는 관리자 계정으로 RDP 접속 후 내부에서 직접 조치하는 방법을 최우선으로 고려
- 근본 원인(권한 없는 그룹)을 고쳤으면 GPO 기본 설정(Preferences → 로컬 사용자 및 그룹)으로 자동화해 재발을 막는다
